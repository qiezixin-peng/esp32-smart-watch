### 3. C3 传感器：MAX30102 Error 263 系列修复（v27→v31）

- **代码（v27）**：FIFO 溢出根因 = 默认 400 样本/秒塞满 32 深度 FIFO、主循环 5s 才读。修复：降采样率 + 循环排空 FIFO + 启用 Rollover
- **代码（v28）**：v27 无效。根因：SparkFun MAX30105 库 `setup()` 的 sampleRate 参数要传**寄存器枚举值**（0-7）不是 Hz 数值（50&7=2 实际是 200Hz）；且 while(available()) 排空在共享 I2C 总线上过载。修复：传寄存器值 + 只单次 getIR()
- **代码（v29/v30）**：Error 263 首次 update 仍出现 → 配置后 13s 无 I2C 访问导致接口不稳定 → begin() 中加预热读取；v30 地址探测预热失败
- **代码（v31 结论）**：该模块配置后首次 I2C 事务必然失败（ESP_ERR_INVALID_RESPONSE=263），属模块特性；预热方案被放弃
- **操作问题**：共享 I2C 总线上避免对单设备做大量连续 I2C 事务；库无文档时需读源码确认参数含义
- **代码（LTR390 崩溃）**：MAX30102 失败后 LTR390 初始化失败，`update()` 调未初始化对象 → NULL 指针崩溃 → 加 `if (!_ready) return;`
- **操作问题**：LTR390 室内无阳光时 uv=0 属正常现象，非 bug

### 16. 阶段 3：手表固件端（v27 系列）

- **工程**：新增独立 `wallpaper/` 板块（wallpaperInit/Parse/ProcessPending/Has/Draw）
- **代码**：MQTT 订阅 `data/wallpaper/set` → 解析 URL → HTTP(S) GET → 写 /wallpaper.tmp → 大小校验(>100B) → rename /wallpaper.jpg → 马达震动 + 表盘缓存失效重绘；失败不重试防死循环，无 WiFi 保留待下载
- **操作问题（分区无需改动）**：实测当前分区表 app0/app1 各 6.4MB + spiffs 3.4MB → LittleFS 直接挂载现有 spiffs 分区，零分区风险

- **操作问题（编译踩坑）**：TJpg_Decoder `drawFsJpg` 参数顺序是 (x,y,filename,fs) 而非 (x,y,fs,filename)

- **操作问题（HTTP 400：悬空指针）**：`WiFiClientSecure client` 声明在 `if` 块内（局部变量），`http.begin(client,url)` 只存指针，块结束 client 析构 → 后续 GET 操作悬空对象 → TLS 未建立但 TCP 已连 → **明文 HTTP 发到 HTTPS 端口**，服务器 400（响应体 `The plain http request was sent to https port`）。修复：client 提升到函数级
- **验证**：v27 编译 SUCCESS（RAM 20.8% / Flash 58.2%）

- **操作问题（方向语义）**：左滑=下一个（与表盘 tab 统一）；v29x 的"连跳"判断为误诊

### 22. 表盘背景图文字融合（核心专项）

- **代码（需求演进）**：用户多次要求"文字直接印在背景上"——无黑框、无挖空遮罩、允许压在主体上。实现：先画背景（JPEG 全屏）→ 文字用半透明色直接叠加 → 消除三块黑框
- **代码（快照机制）**：背景图 + 表盘合成后缓存到快照，避免每次重绘 JPEG 解码（内存/性能优化）

## 七、云平台（ThingsCloud）专项

### 25. 设备接入与数据上报（MQTT）

- **工程**：手表 ESP32 作为 MQTT 设备接入 ThingsCloud（client ID / 用户名 / 密码 = 设备证书三件套）；上报周期 40s（30s 曾触发流控）；上报字段：temp/hum/press/bpm/spo2/uv（即时）+ rssi/uptime/steps/dist/cal（周期）
- **代码**：连接失败退避重连（30s/60s/180s 递进）；CONNACK 等待 2s→5s（服务器实测响应 3s+，2s 误判失败）
- **操作问题（CONNACK 诊断法）**：TCP 通但 CONNACK 不回时，用 PC 以固件同凭据做原始 MQTT 握手，10 分钟区分云侧/设备侧：**匿名能回 rc=4 = broker 活着；带凭据不回 = 云侧设备状态问题**（配额用尽/设备被停用/凭据被重置）

### 26. 主题命名空间与下行通道

- **代码（关键平台特性）**：ThingsCloud **不路由裸 topic**（发布成功但回读收不到）→ 设备有独立主题命名空间，只路由标准主题：属性下发 `attributes/push`、命令下发 `command/send/+`、自定义数据下发 `data/<identifier>/set`
- **工程**：自定义数据流两条——`notify`（通知下发）、`wallpaper`（背景图下发）
- **操作问题（应用端 API 三层格式差异）**：API body 必须 `{"type":"json","msg":{...}}` 包装 + URL 带 `?push_mode=mqtt`；平台剥掉包装后设备端收到**裸 JSON** → 手表端解析代码与 API 请求格式解耦

### 27. 配额与消息量管理（免费版实战）

- **操作问题（413 每日上限）**：每日总消息量达上限后平台立即停止收发，直到次日零点清零自动恢复（官方文档确认）
- **操作问题（隐形消耗源）**：小程序云函数定时触发器每分钟调 ThingsCloud API（2880 条/天）、7×24 运行——用户不操作小程序也在烧配额，曾导致设备被静默拒绝连接
- **修复**：① 云函数触发器删除（config.json `triggers:[]`）② 改为"打开小程序才采集"（页面手动调云函数）③ 首页 30s 轮询不再调 API（只查本地云数据库）→ 每天从 2880 条降到几十条
- **操作问题（触发器部署坑）**：微信开发者工具「上传并部署」只同步代码、**不删除云端已有触发器** → 删除触发器必须单独右键「上传触发器」把空配置覆盖到云端，或在云开发控制台手动删

## 八、工程规范总结（贯穿全程）

1. **版本管理**：T-Watch v14→v29 系列、C3 v26→v47，每次改动前备份到 `backups_*/` 或 `*.before_*`
2. **编译验证**：每步 `pio run` 通过（记录 RAM%/Flash%），再交付真机
3. **真机优先**：大量 bug 只有真机才能暴露（BMA423 地址 0x19、GPIO35 硬件 LOW、FT6336 坐标翻转、LTR390 无阳光 uv=0）
4. **资源约束**：ESP32 堆内存紧张（天气 SSL -10368/-32512、JPEG 解码），全部用"低内存保护/降级/缓存"策略解决
5. **平台特性**：ThingsCloud 主题命名空间只路由标准主题、应用端 API 三层格式差异、免费版 7 天数据/每日消息量限制（云函数触发器删除后消息量停止上涨）
6. **编码卫生**：串口英文（防乱码）、注释中文（便于答辩）、大段替换后必须语法检查（drawBars 教训）
